# Phase 3 — Secure Uploads

## BEFORE

### 1. The threat model for an upload endpoint

An upload endpoint accepts arbitrary bytes and an arbitrary name from the internet. What can go wrong:

| Attack | Example | Defence in this phase |
|---|---|---|
| Path traversal | name `../../etc/passwd` | Keys are generated by us (Phase 2); names cleaned to their last segment |
| Spoofed display name | `invoice‮txt.exe` shows as `invoiceexe.txt` | Strip control and bidi-override characters |
| Malware distribution | upload `.exe`, share the link | Block executables by extension **and** by content |
| Lying Content-Type | HTML uploaded as `image/png` | Detect the type from the first bytes; never trust the claim |
| Stored XSS | `.html`/`.svg` opened inline runs script on our origin | Store active types as `application/octet-stream`, send `nosniff`, always `attachment` |
| Storage exhaustion | one user uploads until the disk is full | Per-user quota |
| Password guessing | thousands of login attempts | Rate limit on `/auth/*` |
| Clickjacking, caching of private data | API response cached by a proxy | Security headers, `Cache-Control: no-store` |

### 2. Why sniff instead of trusting Content-Type

`Content-Type` in a multipart upload is set by the client, so it can be anything. File formats start with
**magic numbers** (`%PDF-`, `\x89PNG`, `MZ` for Windows executables). Checking those is cheap (16 bytes)
and can't be faked without breaking the file itself.

### 3. Status codes chosen

| Situation | Code | Why |
|---|---|---|
| Executable | **415** Unsupported Media Type | The type itself is refused |
| Over quota | **403** Forbidden | Allowed in general, not for this user right now (what Google Drive returns) |
| Too many auth attempts | **429** + `Retry-After` | Standard; tells clients when to retry |

## AFTER

### Files

```
backend/src/upload-policy.ts    sanitizeFilename, sniffContentType, checkUpload (415 for executables)
backend/src/security.ts         securityHeaders middleware, rateLimit() fixed-window limiter
backend/src/routes/files.routes.ts   uses both; adds quota check and GET /files/usage
frontend/src/Files.tsx          storage usage bar (turns red above 90%)
```

New settings in `.env` (all optional): `MAX_USER_STORAGE_BYTES` (default 1 GiB), `AUTH_RATE_LIMIT`
(default 20 requests per IP per 15 minutes).

### Upload pipeline now

```
multer (size limit) → sanitizeFilename → checkUpload (block exe, decide type) → quota check
  → PutObject → INSERT row
```

### Decisions

- **Filename rules:** NFC-normalise, remove control and bidi characters, keep only the last path segment,
  trim, `.`/`..` become `unnamed`, clip to 255 UTF-8 bytes **keeping the extension and never splitting a
  character**. Hidden files like `.bashrc` stay allowed — they're not a path trick.
- **Executables blocked two ways:** extension list (similar to what Gmail blocks) **or** executable
  signature (`MZ`, ELF, Mach-O). Renaming `virus.exe` to `cat.jpg` still gets 415.
- **Type stored = sniffed type** when recognised. `.docx`/`.xlsx` are zip files inside, so a specific
  `application/vnd.*` claim beats a generic zip signature.
- **Active types** (`text/html`, `image/svg+xml`, XML, JavaScript) are stored as
  `application/octet-stream` so no browser will ever render them from our origin.
- **Rate limiting is written by hand** (~30 lines, fixed window, memory bounded) instead of adding
  `express-rate-limit`. Same behaviour for one process.

### Tests (49 passing, +26)

- Unit: 10 filename cases incl. RTL override and NFC; byte clipping on multi-byte names; sniffing;
  type decisions; executable blocking three ways; rate limiter window, per-key counting, reset.
- Integration: renamed `.exe` → 415 with nothing stored; PNG claimed as `text/plain` stored as
  `image/png`; HTML stored as octet-stream; quota (3 × ~1 MiB fills a 3 MiB quota → 403, other user
  unaffected, `/files/usage` exact); security headers present and `X-Powered-By` absent.

### Known limitations

| Limitation | Why it's acceptable now | When to fix |
|---|---|---|
| No antivirus scan (ClamAV) | Executables are blocked; scanning needs another service | Before real users |
| Quota check is racy: two concurrent uploads can overshoot by one file | Bounded by `MAX_UPLOAD_BYTES` | Lock per user if exact quotas matter |
| Rate-limit counters are per process and reset on restart | One process locally | Redis when scaling (Phase 15) |
| Behind a proxy (e.g. Vite dev server) every client has the same IP | Local only | `trust proxy` in the containerised setup (Phase 13) |
| Magic-number table covers ~8 formats | Unknown types fall back safely | Use libmagic if labelling matters |
